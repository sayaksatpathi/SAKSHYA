# SAKSHYA Security Model

The security model of SAKSHYA ensures that evidence is cryptographically verified from the moment of ingest (Acquisition) through to the courtroom (Reporting).

## Core Principles

1. **Integrity Detection**:
   When evidence is ingested, it is immediately hashed (SHA-256). SHA-256 provides a cryptographic integrity fingerprint/content identifier for the evidence object.
   - SHA-256 detects changes.
   - SHA-256 alone does not prevent changes.
   - SHA-256 alone does not establish authenticity.
   - SHA-256 does not make evidence immutable.

2. **Provenance/History**:
   Every action (ingest, AI analysis, export) generates a `ChainEvent` on the **append-only ledger**.
   `event_hash = SHA256(canonical_json(event_data + previous_hash))`

3. **Aggregate Integrity Verification**:
   Instead of verifying thousands of files individually, a **Merkle Tree** aggregates evidence hashes into a single `Merkle Root` to provide aggregate integrity verification.

4. **Logical Immutability**:
   Logical immutability is enforced by application design (original files are never modified in-place); OS-level write protection is deployment-dependent.

5. **Independent Trust Anchor**:
   To prevent an insider threat, a conceptually separate **Trust Authority** signs a canonical structure containing the Merkle Root, Chain Head, Timestamp, and Manifest Hash. The trust signing secret is not stored in SQLite, evidence storage, source code, frontend JS, or the Git repository.

## The Trust Authority

The Trust Authority is conceptually separate from the investigator's ordinary database. It signs a canonical structure containing:

```json
{
  "case_id": "...",
  "merkle_root": "...",
  "chain_head": "...",
  "manifest_hash": "...",
  "timestamp": "...",
  "authority_key_id": "...",
  "algorithm": "HMAC-SHA256"
}
```

The resulting trust receipt is stored on the investigator's system.
**Security Guarantee**: An attacker who controls only the investigator workstation cannot generate a new valid trust receipt without access to the Trust Authority secret.
**Limitation**: If the Trust Authority itself is compromised, its signing authority must be considered compromised.

*Note on Future Production Deployments: Production deployments should prefer an asymmetric digital signature scheme so investigators can verify signatures using a public key without possessing the signing secret.*

## Cryptographic Primitives

- **File Hashing**: SHA-256 (`hashlib.sha256`) - for integrity detection.
- **Signatures**: HMAC-SHA256 (`hmac.new`) - for independent trust anchor sealing.
- **Canonicalization**: JSON attributes are sorted alphabetically with no extraneous whitespace before hashing to ensure determinism.

## Final Security Language
The system is **integrity-protected**, **tamper-evident**, **independently sealed**, **cryptographically verifiable**, and provides an **append-only** ledger.

## Threat Model

### 1. Evidence modification
**Scenario**: An attacker modifies an MP4 file on disk.
**Status**: Mitigated (tamper-evident). The system re-hashes the file and compares it to the original SHA-256 hash.

### 2. Database manipulation
**Scenario**: An attacker gains SQL access and alters metadata or AI results.
**Status**: Mitigated (tamper-evident). Changes invalidate the chain of custody sequence hashes.

### 3. Ledger rewriting
**Scenario**: An attacker rewrites the SQLite ledger to fix broken hashes.
**Status**: Mitigated. The attacker cannot forge the HMAC-SHA256 signature generated by the Trust Authority without the secret key.

### 4. Trust Authority compromise
**Scenario**: The Trust Authority secret is stolen or the service is breached.
**Status**: Out of scope (Limitation). If the Trust Authority is compromised, its signatures can no longer be trusted.

### 5. Private-key/secret compromise
**Scenario**: The HMAC secret is hardcoded or leaked.
**Status**: Partially mitigated. Secrets are loaded via environment variables and not stored in code, but OS-level compromise could expose them if running on the same host.

### 6. Model replacement
**Scenario**: An attacker swaps the local AI models to force false identifications.
**Status**: Partially mitigated. Expected to be mitigated by OS-level access controls and file permissions.

### 7. Malicious evidence upload
**Scenario**: A file designed to exploit parsing vulnerabilities (e.g., ffmpeg exploits).
**Status**: Partially mitigated. The system isolates processing, but underlying parser CVEs could still trigger.

### 8. Path traversal
**Scenario**: Evidence filenames include `../` to overwrite system files.
**Status**: Mitigated. The application sanitizes paths and generates UUIDs for storage.

### 9. Command injection through media tools
**Scenario**: Malicious filenames passed to `ffprobe`.
**Status**: Mitigated. Python's `subprocess` is used with arguments safely passed as lists, avoiding shell injection.

### 10. Report modification
**Scenario**: An exported PDF report is modified before court submission.
**Status**: Mitigated. The generated PDF includes cryptographic hashes of the evidence that can be independently verified against the original files.

### 11. Timestamp manipulation
**Scenario**: Modifying the system clock to forge event times.
**Status**: Partially mitigated. The Trust Authority stamps the receipt with its own time, but the local ledger relies on system time.

### 12. Unauthorized workstation access
**Scenario**: Physical or remote access to the forensic workstation.
**Status**: Out of scope. Security depends on OS-level access controls, full disk encryption, and physical air-gapping.
